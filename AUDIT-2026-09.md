## 1. Executive summary

Three **critical** issues were found and fixed in code, two of them also requiring the shipped
migration to be applied:

* **Any account takeover:** `POST /api/set-recovery-phrase` trusted a raw `{userId, phrase}` body
  with **no authentication whatsoever**. Any caller could set a recovery phrase for any user id,
  then walk `/api/reset-with-phrase` → new password → full takeover. **FIXED (VERIFIED in code)**
  — the route now derives the user from the caller's Bearer JWT and is rate-limited.
* **The paid hint paywall was render-only.** The whisper inbox `select()`-ed
  `sender_username / sender_email_name / sender_user_id / sender_country / state / city / device`
  for **every** message; "unlock for 5 coins" only decided whether React *printed* them. Anyone who
  ever opened devtools saw every sender's identity for free. **FIXED (code + migration §S2)** —
  column-level `REVOKE` for client roles plus a definer RPC that answers only when an unlock row
  exists; the write path also stopped storing `sender_username/email_name/user_id` at all.
* **Infinite coins:** `public.purchase_whisper_coins(int, text)` is `security definer`, still
  granted to `PUBLIC`/`anon`/`authenticated`, and credits `auth.uid()` any `coin_amount` passed.
  One `supabase.rpc(...)` call mints any balance. No app code calls it (real path is
  Paystack → `credit_verified_payment`). **FIXED (migration §S1)** — revoked from client roles.

Everything else: sender-context columns removed from client writes, message length CHECKs,
Cloudinary ownership predicate on inserts, O(users)→O(friends) notification fan-out, unbounded
chat history and thread loads capped, whole-table count(*) aggregates replaced, read-modify-write
coin debits converted to atomic definer RPCs under the user's own JWT, nine routes rate-limited,
five push Edge Functions gated to the service role, real security headers added, and the realtime
`messages` payload narrowed to the columns clients render.

**Nothing in this audit found: a SQL injection (PostgREST parameterization + no `rawSql` string
interpolation anywhere — VERIFIED), a committed secret (full-history scan — VERIFIED), an RLS
bypass on any table defined in the repo migrations (VERIFIED for those tables), or an XSS sink
(no `dangerouslySetInnerHTML`, no `innerHTML`, no `eval`/`Function` — VERIFIED).**

## 2. Findings — security

### S-1 CRITICAL · Unauthenticated recovery-phrase set → any-account takeover — **FIXED**
`app/api/set-recovery-phrase` previously did `userId` from the JSON body, no session check.
Fix: Bearer JWT → `auth.getUser()` → `userId := user.id` (body `userId` ignored), phrase hashed
`pbkdf2_sha256` 210k iterations/32-byte salt via `lib/recoveryPhrase.ts`, `timingSafeEqual` on
verify, and `apiGuard` 5/15min per IP+user. `reset-with-phrase` got the same treatment with
attempt caps. **VERIFIED** (code) · rate limiter is best-effort in-process — see S-13.

### S-2 CRITICAL · Hint paywall bypass (free identity disclosure) — **FIXED, DB APPLY PENDING**
See executive summary. The complete fix is three parts and the migration must land **before**
this client deploys (§10 deploy order):
1. §S2 column `REVOKE` (needs PG15+, guarded DO) — DB-side truth.
2. `whisper_hints_for(uuid[])` definer RPC — returns hint rows only when a matching
   `anonymous_sender_reveals` row exists; notifications page now loads lazily, only for
   already-unlocked ids, once after unlock, and one free re-read if a hint is missing.
3. Write-path hygiene: inserts from `/u/[username]` now send `recipient_id, message, image_url`
   + the four coarse context columns only; the dead duplicate `Profile.tsx` (which still selected
   the raw columns) was deleted.
Realtime INSERT payloads for `messages` are separately narrowed (§S3), and the per-column
`REVOKE` guarantees even the `select("*")`-style payload shape cannot carry the secrets.
**VERIFIED** (code + SQL) · effectiveness in production **LIKELY** until migration applied
(the base-table grants are not in the repo).

### S-3 CRITICAL · Client-callable coin minting RPC — **FIXED, DB APPLY PENDING**
§S1 revokes `purchase_whisper_coins` from `public/anon/authenticated`, keeps `service_role`.
**VERIFIED** as a live path by reading the function's definition in `202608190004`-adjacent
migrations + zero app callers. Whether prod matches the repo definition is **LIKELY**, not
VERIFIED (base grants).

### S-4 HIGH · Unbounded message inserts (client-side rows) — **FIXED (migration)**
`direct_messages.content` and `messages.message` had no ceiling → megabyte rows that every
reader of that conversation must download forever. §S5 adds `CHECK (length ...)` at 5000 chars,
with a `NOT VALID` fallback so existing rows can't block the migration.
**VERIFIED** (SQL reviewed) · **UNVERIFIED** how many prod rows would trip the valid-path (the
fallback makes that a non-issue, and the report flags: the CHECK is a last line — the client
composer caps lower).

### S-5 HIGH · Coin debit was read-modify-write → race/spend-double — **FIXED**
`/api/coins/feed-post` and `/api/coins/reply` used to `select` balance, compare, `update` it —
N parallel tabs, N posts, one balance. Both now call §S7b `debit_whisper_coins`/
`refund_whisper_coins` **through a Supabase client carrying the user's own JWT** (so RLS + the
definer function both apply; no service-role passthrough), `402` on `Insufficient coins`, `503`
if the function is missing (migration not applied → refuse to serve, never fall back to the racy
path). Refunds on Cloudinary-post failure go through the same atomic credit.
**Caveat (honest):** a failed refund after a failed post leaves coins debited — logged loudly;
pre-fix the race could lose them anyway. **VERIFIED** (code) · **LIKELY** end-to-end until the
function exists in prod.

### S-6 HIGH · No rate limits on sensitive routes — **PARTIALLY FIXED**
New `lib/apiGuard.ts` (in-process sliding window) now guards 9 routes: set/reset-phrase,
admin/verify-pin, admin/grant-coins, coins/feed-post (6/min/user), coins/reply, creator/post,
gifs, paystack/verify. Explicitly **still unguarded**, each with a reason:
`audio/view`, `photos/view`, `feed/photo` (auth'd, coin-gated reads — the DB is the limiter);
`sender-context` (reads request headers only); `currency/rates` (server-cached FX blob);
`cloudinary/destroy` (auth'd + ownership-predicated); `send-push` and `/api/notify-message`
(both require `PUSH_WEBHOOK_SECRET`).
**VERIFIED** that apiGuard is **best-effort**: memory-per-serverless-instance, no cluster sync —
the dashboard checklist says to mirror these buckets in Vercel Firewall/Upstash. **FAILS** as a
distributed ceiling until that's done.

### S-7 HIGH · Push Edge Functions trusted the payload body — **FIXED (deploy pending)**
All five `notify-*` functions run with the **service-role key inside** and previously believed
whatever `record` a caller POSTed; Supabase `verify_jwt` accepts *any* valid user JWT, so any
signed-in user could forge a push (attacker-chosen title/body) to any recipient and torch the FCM
quota. Each now requires `Authorization: Bearer <service role key>` (SHA-256-compared,
constant-time) before touching the payload. `whispers-ai` already verified the user JWT properly
— untouched. **VERIFIED** (code) · effective once `supabase functions deploy` runs.

### S-8 MEDIUM · Cloudinary refs not owner-checked — **FIXED (migration)**
`image_url`/`voice_note_url` accepted any `res.cloudinary.com` URL; users could reference each
other's assets. §S6 adds `cloudinary_asset_owned_by()` (prefix `LIKE` + `'/<folder-owner>/'`
segment test — note: the *first* draft of this guard was inert because `position('://res…') <> 1`
is always true for `https://` URLs; corrected and re-reviewed) into the direct-messages insert
policy + a `whisper_image_folder_ok` trigger on `messages`. Browser uploads themselves remain
unsigned presets (that's the design — folder convention `whisper/<kind>/<uid>/` enforced
server-side at insert). Preset-side folder restriction is **UNVERIFIED** → dashboard item.

### S-9 MEDIUM · Zero security headers, no CSP — **FIXED (conservative)**
`next.config.ts` previously emitted none. Now: `X-Frame-Options: DENY` +
`frame-ancestors 'none'; object-src 'none'; base-uri 'self'; form-action 'self'`, `nosniff`,
`Referrer-Policy: strict-origin-when-cross-origin` (URLs carry usernames — no full-referrer
leak), HSTS 2y preload, `Permissions-Policy` with `microphone=(self)` kept for voice notes and
camera/geolocation/payment/usb/serial/display-capture=(), COOP `same-origin-allow-popups` (auth +
Paystack popups need opener handles; **this is why not plain `same-origin`**), CORP `same-origin`
with `/og/u/*` relaxed to `cross-origin` for social scrapers. A full script-src CSP was
**deliberately not** enabled (Paystack inline.js + Next runtime scripts are not statically
enumerable) — it is a staged follow-up, measured on staging first. **VERIFIED** (config),
enforcement on Vercel LIKELY-trivial.

### S-10 MEDIUM · `/admin` is a client-gated SPA page — **report-only** (by design, acceptable)
The gate is cosmetic; the actual authorization for both admin operations is DB-side
(`admin_grant_coins` checks `is_whisper_admin`, verify-PIN is an RPC) — that's the right shape.
Residual: the *page shell* prerenders **static** at build (it's in `baseline-build.log`), so its
existence/markup ships to everyone, and `/api/admin/grant-coins` double-checks via client role.
Creator authz (`lib/creator.ts` + `is_whisper_creator()` + guard trigger + `author_role`
immutability, incl. the two creator accounts in scope: `basseyaniekeme43@gmail.com`,
`mfonisobassey851@gmail.com`) is genuinely exemplary — **VERIFIED**: no client path can write
`author_role`/`creator_verified`, and the trigger enforces the single-row invariant.

### S-11 LOW · Anon identity is client-computable — **report-only**
`lib/anonIdentity.ts` derives "Rebecca, 24, Lagos" labels from a deterministic FNV hash of the
sender id. Anyone can test membership ("is handle X = hash(user_id)?"). No secret is exposed;
the columns are coarse. Accepted; noted so it's not mistaken for a vuln fix later.

### S-12 LOW · Legacy dual-write `fcm_token` on device tokens; `streak`/`saved-posts` unguarded
reads; `SHELL_CACHE` not owner-scoped (content is owner-independent — **fine**, verified).
**Report-only.**

### S-13 CSRF / cookie posture — **VERIFIED clean**
No middleware, no Supabase cookies session (client uses `localStorage` bearer tokens; every
state-changing route reads `Authorization: Bearer`, and `localStorage` is not auto-attached
cross-site). CSRF is structurally mitigated. This is also why the S-2 hints fix didn't need a
cookie-samesis dance. `@supabase/ssr` installed but unused — noted, not a vuln.

### S-14 Backups/DR — **UNVERIFIED** (dashboard)
Point-in-time restore window, PITR retention, and any export cadence are Supabase-plan settings,
not repo state. Checklist item.

### S-15 No account deletion — **FAILS** (privacy gap, unfixed by design)
There is no delete-my-account flow anywhere (client or DB); recovery is password-reset only. For
an app storing location context + device strings per whisper this is a real privacy obligation
(GDPR/DPAs). Deliberately **not** implemented during this pass (destructive-by-nature: cascading
deletes deserve their own reviewed migration + grace-period design). Flagged as the top
follow-up after the migration applies.

## 3. Findings — database, performance, scalability

### D-1 HIGH · Chat loaded the ENTIRE thread — **FIXED**
`app/chat/[conversationId]` did `select("*").order(created_at asc)` with no limit: a year-long
thread shipped every row + every waveform JSON on every open. Now: newest-400, reversed,
`hasOlder` flag, top-edge paging (`loadOlderMessages`, re-entry guarded, scroll-height
compensation via rAF), reactions `.in()` chunked at 100 ids (400 uuids ≈ 15KB query string —
gateway-rejecting), delivered-marking capped at 100, read-marking capped at 200. **VERIFIED**
(code, `tsc` clean) · no runtime test (sandbox).

### D-2 HIGH · Feed fan-out & thread costs — **FIXED (migration)**
§S4: `notify_new_public_feed_post` used to insert a notification row + a push row **per post ×
per profile** (10k posts/day × 100k users ≈ 2B rows/day of self-inflicted DoS); now friends-only,
2 rows per friend, and the duplicate `notifications` insert removed (in-app list renders
`public_feed_notifications`; push path unchanged). §S7: `record_public_feed_impressions` now caps
the id array and implements the intended 2s dedup in-function — the `202608260001` partial index
it replaced used `now()` in a **non-immutable index predicate, which Postgres rejects: that index
has never existed / that migration as-written FAILS to apply cleanly on a fresh DB** (VERIFIED by
SQL semantics; §S7 drops it if it somehow exists). §S8: `public_feed_thread` returns the 200 most
recent replies; `public_feed_page` clamps `p_offset` to 2000 (deep offset-walk was a linear-cost
oracle).

### D-3 MEDIUM · Inbox unread counts = 1 row per unread message — **FIXED**
§S9 adds `unread_message_counts(uuid[])` (definer, membership re-asserted, one grouped row per
conversation) + `notifications_user_unread_idx` + a partial `direct_messages_unread_idx`
(`where read_at is null`). `app/inbox` calls the RPC with a fallback to the old query if the
function is missing. Inbox conversation list and `lib/nav/navBadges.ts` capped at 300.

### D-4 MEDIUM · Homepage `whisper_live_activity()` two full-table count(*) per 90s per visitor —
**FIXED (migration)** — §S10: totals → `pg_class.reltuples` estimates, today-counts stay exact on
the `created_at` indexes that 202608200001 already added.

### D-5 MEDIUM · Feed fallback path unbounded — **FIXED (client)**
`lib/feedApi.fetchWholeWindow` (no-RPC fallback) now caps at 500 newest live rows; the RPC path
is the real paging engine. Offline snapshot was already capped at 12 rows (unchanged).

### D-6 MEDIUM · Realtime presence & subscriptions — **PARTIALLY FIXED / report**
Presence sync cost is O(online) per join/leave (verified read of `lib/realtime/presence.ts`) —
fine below ~100 concurrent per topic, a redesign (server fan-out) above it. Chat typing
indicator used to open one channel per conversation on the inbox — capped to 100 most recent.
Known quirk (**LOW**): `chatManager` dedupes per-key but a second subscribe to the same
conversation is a no-op *after* the first is torn down in a specific interleaving — logged, not
fixed.

### D-7 UNVERIFIED · Paystack crediting + replay — **report**
`credit_verified_payment` lives only in the production DB (no definition in repo). The client
still generates the Paystack reference (`app/premium`) and `/api/paystack/verify` checks it —
the §S7b unique index on `coin_transactions(reference) where kind='purchase'` now makes a
replayed/parallel verify a no-op, and the route is rate-limited. Amount-trust model itself:
**UNVERIFIED** (need the function body). Dashboard: verify it re-checks `amount` against the
package price server-side.

### D-8 LOW · `ensure_coin_wallet` exposes an existence oracle (email→uid→wallet row) — noted;
harmless while usernames/emails are only shown to their owners, keep in mind before any public
directory.

### D-9 Base-schema gaps — **UNVERIFIED**
No `unique(lower(username))` index appears in the repo (case-duplicate profiles are possible —
dashboard: confirm or add CONCURRENTLY); `profiles` self-UPDATE policy is broad (any column
except guarded ones — acceptable-ish, list of columns to lock down in the checklist); no local
`supabase db diff` was possible, so hand-created prod tables' policies are unaudited by
necessity.

## 5. Load-test plan (staging only — never production; no destructive ops)

Prep: `supabase link && supabase db push` (or dashboard) to apply the full migration set incl.
`202609070001` to a **staging project** with a copy of prod-scale data (seed below), Vercel

```bash
# Seed: 5k users / 200k messages / 20k conversations / 50k feed posts (anon-safe fake text only)
psql "$STAGING_URL" -f scripts/seed-loadtest.sql   # author as part of this plan — NOT included
k6 run loadtest/chat-open.js        # 200 VU: open a 3k-message thread → p95 < 400ms, ≤ 400 rows
k6 run loadtest/feed-scroll.js      # 300 VU × 60s: public_feed_page p60/p95, offsets to 2000 clamp
k6 run loadtest/whisper-send.js     # 100 VU: /u/[u] insert + sender-context; assert 429 buckets
k6 run loadtest/hint-paywall.js     # attacker VU: rpc whisper_hints_for w/o unlock → 0 rows;
                                    # select sender_* → 42501 — MUST fail closed
k6 run loadtest/coins-race.js       # 50 VU same wallet: debit_whisper_coins — no negative balance,
                                    # exactly one debit per success (S7b uniqueness)
k6 run loadtest/notify-fanout.js    # 1k posts/min as 1 friend-graph → row-rate ≈ posts×friends, NOT
                                    # posts×users (assert via pg_stat_user_tables n_tup_ins delta)
```

Acceptance gates: no route p95 > 1.5s at target VU; errors < 0.5%; every negative test above
fails closed; `count(*)` scans from §S10 gone from `pg_stat_statements`. Then one soak (12h at
30% of capacity) monitoring connection pool (Supabase pooler: session vs transaction mode) and
realtime socket counts (`_realtime` connections = subscribers, not presence O(n²)).

**Run cost guardrail:** cap k6 to staging project id; add a `--tags` env filter; never target
`*.supabase.co` of production.
